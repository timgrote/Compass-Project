### 3. Discovered Docker Networking Behavior
**Key Finding:** Docker Desktop on Windows has port forwarding issues with certain protocols

**What Works:**
- ✅ API accessible from inside container (localhost:27123/27124)
- ✅ API accessible from container via Docker bridge (172.17.0.1:27123/27124)
- ✅ Port forwarding exists (netstat shows LISTENING on 0.0.0.0:27123/27124)

**What Doesn't Work:**
- ❌ Windows host → localhost:27123 (HTTP) - Empty reply from server
- ❌ Windows host → localhost:27124 (HTTPS) - SSL handshake failure

**Why This Doesn't Matter:**
- n8n will communicate with Obsidian via **internal Docker network** using container name `http://obsidian-api:27123` or `https://obsidian-api:27124`
- Port forwarding to Windows is only needed for debugging from host machine
- For Phase 2, all inter-service communication bypasses the problematic Windows port forwarding

## Technical Deep Dive

### Obsidian Stability Flags Explained
- `--no-sandbox`: Disables Chrome sandbox (required in containers)
- `--disable-gpu`: Disables GPU acceleration (prevents crashes in containerized environments)
- `--disable-dev-shm-usage`: Avoids using /dev/shm (limited in Docker)
- `--disable-software-rasterizer`: Disables software rendering fallback
- `--disable-features=VizDisplayCompositor`: Disables hardware composition layer

### Docker Networking Architecture
```
Windows Host (127.0.0.1:27123)
    ↓ [Port Forward - BROKEN on Windows]
Docker Desktop WSL2 Backend
    ↓
compass-net Bridge Network (172.18.0.0/16)
    ↓
compass-obsidian container (172.18.0.x:27123)
    ↓ [WORKS PERFECTLY]
Obsidian REST API (0.0.0.0:27123)
```

**Why Windows Port Forwarding Fails:**
- Docker Desktop uses WSL2 backend with network translation
- Some protocols (especially HTTP with immediate close) don't translate correctly
- SSL/TLS handshake fails due to certificate validation across the boundary
- This is a known Docker Desktop limitation, not our configuration issue

**Why This Is Fine for Production:**
```
n8n container (172.18.0.y)
    ↓ [Direct Docker network communication - WORKS]
http://compass-obsidian:27123
    ↓
Obsidian REST API
```

### REST API Plugin Configuration
**Location:** `/config/Compass/.obsidian/plugins/obsidian-local-rest-api/data.json`

**Key Settings:**
```json
{
  "port": 27124,
  "insecurePort": 27123,
  "enableInsecureServer": true,
  "enableSecureServer": true,
  "bindingHost": "0.0.0.0",
  "apiKey": "[generated key]",
  "crypto": {
    "cert": "[self-signed certificate]",
    "privateKey": "[private key]"
  }
}
```

**Security Notes:**
- Self-signed certificate auto-generated by plugin
- Valid for 365 days
- API key must be included in Authorization header: `Authorization: Bearer [key]`
- In production, consider disabling HTTP port (27123) and using only HTTPS

## API Endpoints Reference

## Lessons Learned

### 1. Docker Desktop Limitations
- Port forwarding on Windows/WSL2 is unreliable for certain protocols
- Always test inter-container communication on the Docker network, not via localhost
- For Phase 2, n8n will bypass this issue entirely

### 2. Electron in Containers
- GPU acceleration must be disabled
- Shared memory usage must be disabled
- Standard Chrome flags don't always work; need container-specific flags
- Autostart configuration persists in `/config/.config/autostart/`

### 3. Configuration Management
- Plugin settings can be extracted with `docker cp`
- Configuration is separate from vault data
- Template includes plugins but users can customize after first run
- API keys in config are okay for local deployment (not exposed to internet)

### 4. Security Considerations
- API key is randomly generated and strong
- Self-signed certificate is fine for local Docker network
- Consider regenerating API key before sharing vault template publicly
- HTTP port should be disabled in production (only HTTPS)
